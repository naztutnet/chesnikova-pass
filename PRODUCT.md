# CHESNIKOVA PASS — адаптивный веб-сайт

## Понимание задачи

Веб-сайт для сотрудников и координаторов «Амедиа»: пользователь оформляет пропуск с телефона или компьютера, проверяет итог и только после явного подтверждения отправляет заявку во внешний PassOffice.

Первая версия сейчас работает как безопасный интерактивный прототип. Она не входит в PassOffice и не создаёт реальные заявки.

## Подтверждённая карта PassOffice

- Для корпоративной учётной записи требуется режим авторизации Active Directory.
- Кнопка «Разовый» сразу создаёт пустой черновик и назначает ему ID — открытие формы уже является внешним изменением.
- Обязательные поля заявки: дата посещения и комната/павильон.
- Обязательные поля посетителя: фамилия, имя и отчество.
- Необязательные поля: организация, дата рождения, иностранное гражданство и фотография.
- Доступен импорт файла со списком посетителей и ручное добавление нескольких гостей.
- В списке подтверждены статусы «Черновик», «Согласовано» и «Обработано».
- Сам ID не доказывает отправку: он появляется у пустого черновика. Успех отправки нужно проверять по ID и изменению статуса с «Черновик».

## Архитектурные допущения

- Основной пользователь — координатор, оформляющий разовые пропуска для гостей.
- Отправка в PassOffice будет выполняться сервером, а не браузером пользователя.
- Перед реальной отправкой всегда показывается полное резюме и требуется отдельное подтверждение.
- После отправки успех подтверждается повторным чтением строки по ID и ожидаемым изменением статуса.
- Ручной и свободный ввод собирают одну и ту же модель заявки и проходят общую финальную валидацию.

## Критически недостающие сведения

- Значения и правила поиска в справочнике организаций.
- Формат файла массового импорта посетителей.
- Полный переход статусов после кнопки «В обработку» и возможные сообщения об ошибках.
- Роли пользователей и кто выдаёт доступ.
- Достоверный признак успешного создания заявки.
- Сервер, домен и способ авторизации пользователей рабочего сайта.

## Основной путь

```text
Заявки → Новая заявка → Способ ввода → Детали визита → Посетители → Проверка
                         ↳ свободный текст → распознанный черновик ↗
                                                               ↓
                                                  Явное подтверждение
                                                               ↓
                                                 Отправка в PassOffice
                                                               ↓
                                          Проверенный номер и статус заявки
```

Ошибки отдельных полей возвращают пользователя к конкретному шагу, не стирая черновик.

Подробная логика меню, этапов и восстановления описана в `UX_FLOW.md`.

## Роли первой версии

- Владелец: управляет администраторами и настройками интеграции.
- Администратор: выдаёт и отзывает доступ, видит технические статусы без секретов.
- Координатор: создаёт и просматривает только разрешённые ему заявки.
- Демо-пользователь: проходит весь сценарий без обращения к PassOffice.
- Без доступа: видит причину ограничения и контакт администратора.

Доступ проверяется сервером при открытии сайта и повторно перед созданием заявки.

## Риски и критерий успеха

- Веб-сессии и права пользователя проверяются сервером; данных из браузера недостаточно для авторизации.
- Пароль PassOffice не хранится во фронтенде, не попадает в браузер и логи.
- Повторное нажатие не должно создавать дубликат: операция получает идемпотентный ключ и блокировку.
- Таймаут после отправки означает «результат неизвестен», а не автоматический повтор.
- Успех фиксируется только после повторного чтения PassOffice и нахождения созданной заявки.

## Визуальная система

- один гротеск Onest во всём интерфейсе;
- графит `#111214` для текста и основных действий;
- бумажный фон `#F7F7F5` и белые рабочие поверхности;
- кобальт `#245DFF` только для действия, активного шага и системного сигнала;
- без отдельного логотипа и тематических кино-метафор на этапе прототипа.
